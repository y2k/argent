# Design

## Context

Мотивация описана в `proposal.md`. `event/dispatch` уже создаёт отложенную операцию, которая получает окружение и вызывает найденный адаптер с `(env, arg)`. `event/register` сейчас оборачивает готовую операцию и игнорирует аргумент. `fx/next` связывает операции, исполняя обе с одним окружением.

В `app.clj` обычные эффекты заданы функциями `[_env arg]`; `:chat:new-message` вручную читает состояние и передаёт окружение в добавление сообщения. `chat/start` возвращает функции `[w node]`; рендереру нужен `w` для контекста Android и callback’ов. Проверка `substituted` подтверждает подмену зависимостей, а `instance-flow` — изоляцию приложений и поведение сообщений.

Изменение затрагивает несколько модулей и контракт регистрации, поэтому нужен общий дизайн миграции.

## Goals / Non-Goals

**Goals:**
- Сосредоточить внутреннюю сигнатуру `(env, arg)` в двух регистраторах.
- Сохранять явную сборку `(-> w ...register...)` и передачу актуального окружения при исполнении.
- Представлять прикладную композицию через `event/dispatch` и `fx/next`.

**Non-Goals:**
- Удаление окружения из инфраструктуры View, новый контейнер зависимостей или глобальный реестр.
- Изменение очередей, формата событий, UI и QR-протокола.
- Совместимость с прежним контрактом `event/register`, автоматическое распознавание возвращённых операций или третий регистратор.

## Decisions

### 1. Два явных регистратора

`fx/register [env name f]` возвращает окружение с адаптером, который вызывает `f` только с аргументом и возвращает результат как есть. `event/register [env name handler]` возвращает окружение с адаптером, который при вызове получает `effect` через `handler(arg)`, исполняет его с текущим окружением и возвращает результат исполнения.

Регистрация и построение `dispatch` не вызывают ни `f`, ни `handler`. Разделение вместо универсального регистратора устраняет неоднозначность: обычное действие вправе вернуть функцию как значение.

### 2. Окружение приходит в адаптер при исполнении

Адаптеры не захватывают исходное окружение. `event/dispatch` сохраняет единый механизм вызова. Альтернатива с привязкой зависимостей при регистрации ломает подмену окружения и существующую спецификацию композиции.

### 3. Миграция по роли функции

- `main/main`: обработчики старта, увеличения и уменьшения становятся функциями аргумента, возвращающими прежние операции; неиспользуемый аргумент обозначается явно.
- `app/create`: состояние регистрируется через `fx/register`; новое сообщение — через `event/register`, чтение состояния и добавление сообщения связываются `fx/next`.
- `app/run`: QR picker, Toast, UI- и domain-доставка регистрируются через `fx/register`; рендеринг — через `event/register`.
- `chat/start`: функции добавления и обновления сообщения принимают узел и возвращают операцию от `w`. Это инфраструктурная граница, где доступ к окружению оправдан.
- Тестовые зависимости в `test/argent/counter.clj` и `test/qr_example.eval` используют те же публичные регистраторы. Подмены операций выполняются повторной регистрацией, данные остаются обычными записями окружения.

`:context` и другие значения данных не являются обработчиками и остаются в map. `:app:start!`, `:app:handle-event!`, `:app:render!` — внешние функции запуска экземпляра, а не операции протокола `(env, arg)`; их сигнатуры сохраняются. Внутри `:app:render!` композицию можно собрать из тех же операций и запустить на границе экземпляра, не вызывая адаптер рендеринга напрямую. Существующие возвращаемые значения инфраструктурных функций, включая `nil` у нового сообщения, сохраняются.

### 4. Проверка контракта через существующие проверки

По результатам ревью согласовано добавление `fx/pure [value]`: операция возвращает значение без действия. Композиция нового сообщения завершается `fx/pure nil`, чтобы результат внешней зависимости добавления сообщения не менял прежний результат обработчика. Проверка использует зависимость, возвращающую ненулевой маркер.

Дополнить существующие проверки передачи аргумента и результата, ленивости фабрики, результата-функции обычного действия и подмены зависимости. Использовать `make check`, затем сборку и запуск на физическом Android-устройстве. Проверить счётчик, новое сообщение, очереди и QR как потребителей изменённых регистраций. QR использует камеру Google Code Scanner; формулировка о выборе изображения в исходной задаче уточнена с пользователем.

## Risks / Trade-offs

- Несогласованная миграция сигнатур приводит к ошибкам арности → обновить регистраторы, все регистрации и тестовые окружения в одной итерации.
- Захват старого `env` нарушает подмену → сохранить проверку `substituted` и явно проверить отложенный запуск с новым окружением.
- Добавление лишнего уровня функции в chat может отложить действие без исполнения → проверить добавление и обновление сообщения через общий dispatch, затем на устройстве.
- В репозитории есть пустой change `simplify-event-registration` → этот план самостоятельный; объединение или удаление другого change не входит в миграцию.

## Migration Plan

Обновить API регистрации и его потребителей совместно; совместимый переходный слой не нужен. Данные очереди не мигрируют, поскольку имена и формат событий сохраняются. После `make check` собрать приложение, установить и запустить на физическом устройстве, проверить основные сценарии. При недоступном устройстве проверка остаётся незавершённой до подключения. Откат — совместное восстановление прежних регистраторов и вызывающего кода; изменения сохранённых данных отсутствуют.
