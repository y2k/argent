# Design

## Context

Мотивация описана в `proposal.md`. Изменение затрагивает диспетчер, Android-доставку и QR, поэтому требует общего соглашения об этапах.

`event/dispatch` возвращает отложенную функцию и вызывает обработчик только после передачи окружения. `app.clj` доставляет UI-события через Handler, бизнес-события через SQLite. `event_pump/step` выполняет handle → ack → render → wake. ID уже доступен при чтении записи. `qr_image.clj` разделяет подготовку модуля, запуск сканера и callbacks; сейчас callback ошибки отбрасывает объект SDK. Eval-проверки используют те же функции без Android.

Проверено, что установленный компилятор принимает `eprintln` для Java, а имеющийся runtime реализует его через `System.err.println`.

## Goals / Non-Goals

**Goals:**
- Добавить наблюдаемость в существующих границах исполнения, сохранив результаты функций и порядок побочных эффектов.
- Читать один формат как в eval stderr, так и в Android logcat.

**Non-Goals:**
- Отдельный сервис логирования, интерфейс логгера, DI-зависимость, уровни, переключатель или файловое хранилище.
- Новая обработка исключений, повторные попытки, изменение доставки и формата SQLite.
- Новые глобальные идентификаторы или дампы объектов приложения.

## Decisions

### Прямой eprintln

Вызовы ставятся непосредственно в точках исполнения. Это выбранный пользователем вариант вместо `android.util.Log` и функции в окружении: он уже доступен общему коду и не требует Android-зависимости диспетчера. Не проводить вывод через `event/dispatch`, чтобы не создавать рекурсию.

Формат: `Argent <этап> key=value`. Имена Y2K keywords выводятся как строки без двоеточия. Одну запись собирать одним вызовом. Метаданные с произвольным текстом (ошибка SDK) привести к одной строке, заменяя CR/LF на пробелы; выводить текст ошибки с типом, без многострочного stack trace. Время, PID и поток предоставляет logcat.

### Исполнение, а не создание вызова

Внутри отложенной функции `event/dispatch` выводить `op.begin name=...`, сохранить результат обработчика, вывести `op.end name=...` и вернуть сохранённый результат. Вложенные вызовы естественно образуют вложенную последовательность. При исключении `op.end` не выводится; исключение распространяется прежним способом. Не добавлять try/finally, который создавал бы ложную отметку успеха.

Все операции общего dispatch покрываются этим местом. Прямые управляющие вызовы `:app:*` из `app.clj` покрываются этапами жизненного цикла, доставки и отрисовки, а не дополнительным механизмом обёрток.

### Очереди и жизненный цикл

- В `app.clj`: `app.start` перед стартом приложения, `app.stop` после штатного освобождения ресурсов.
- Для UI: `ui.enqueue` после постановки callback; внутри callback `ui.handle.begin`, `ui.handle.end`, затем `render.end source=ui` после отрисовки. Записи доставки содержат `event`.
- Для бизнес-очереди: `queue.enqueue event=...` после успешного `queue/push!`. В `event_pump.clj` выводить `queue.handle.begin`, `queue.handle.end`, `queue.ack`, `render.end source=domain`; ID и имя события брать из прочитанной записи. Подтверждение логировать после успешного ack, отрисовку — после render.
- Пустой проход pump не создаёт записи. Формат БД и возвращаемое значение push не менять ради логов: ID нужен на этапе обработки и подтверждения, где уже существует.

### QR как отдельный асинхронный процесс

В `qr_image.clj` отмечать `qr.prepare`, принятый переход к готовности `qr.ready`, `qr.scan.start`, `qr.result status=...` и остановку активного запроса `qr.stop`. Существующий guard фазы определяет, принят ли результат: поздние callbacks не должны выглядеть как доставленный результат. Отметку остановки ставить только при фактическом переходе в done, в том числе при обычном завершении запроса.

В callback ошибки SDK дополнительно выводить `qr.error error=...` с исходным исключением до передачи прежнего `scan-failed`. Успех не выводит содержимое QR. `op.end name=qr:pick` означает возврат из запуска, а не завершённое сканирование.

### Проверка

Сохранение результатов, отложенности и порядка проверяет существующий `make check`. Дополнительно проверить stderr на небольшом сценарии отложенного и вложенного вызова: отсутствие записей до исполнения, порядок begin/end и неизменный результат. Для очереди использовать сценарий с известным ID из `test/event_pump.eval`, без введения подменяемого логгера ради теста.

На физическом Android-устройстве собрать и запустить приложение штатным способом, проверить счётчик, создание сообщения, QR-успех, отмену, доступную ошибку SDK и остановку Activity. Читать `adb logcat -v threadtime 'System.err:W' 'AndroidRuntime:E' '*:S'`, выделяя `Argent`. Если ошибку SDK невозможно воспроизвести, отметить это явно и проверить соответствующую ветвь контролируемым тестом; не считать невыполненный сценарий проверенным.

## Risks / Trade-offs

- Постоянный синхронный вывод добавляет шум и работу на UI-потоке → короткие метаданные, без дампов и логов пустых проходов.
- Logcat имеет ограниченный буфер → считывать трассу во время воспроизведения; долговременное хранение не требуется.
- Наличие `op.begin` без `op.end` само по себе не доказывает исключение (буфер мог быть обрезан) → сопоставлять с AndroidRuntime и соседними этапами.
- Один общий тег `System.err` используется и сторонним кодом → префикс `Argent` отличает записи приложения.

## Migration Plan

Изменения схемы БД и данных не нужны. После автоматической проверки установить обновлённую сборку на физическое устройство и проверить трассу. Откат — возврат предыдущей сборки, без миграции данных.
