# Design

## Context

Мотивация описана в `proposal.md`. `Makefile` запускает шесть eval-групп и `test/logging.py`, который вызывает eval и сравнивает stderr. В `.eval` находятся верхнеуровневые выражения и eval-only `assert`; Java-target требует определения функций. `test/argent/counter.clj` уже содержит тестовые функции, пригодные для переноса.

`build.clj` использует `make` 0.6.0 и `android-build` 0.3.0, генерируя приложение и тесты в разные Android-каталоги. Пакет `make` уже умеет генерировать Java с сохранением структуры каталогов и предоставлять runtime из пакета `prelude/1.0.0` в `y2k/language/language_runtime.java`.

В `qr_image.clj` функция `request` не зависит от Android, но соседствует с импортами Android/GMS и реализацией камеры. Остальные локально тестируемые модули операций, прикладной логики, преобразования узла и прохода очереди платформонезависимы.

JEP 458 (JDK 22) позволяет запускать многофайловую программу через `java path/to/Runner.java`: зависимые исходники ищутся по структуре пакетов и компилируются в памяти. Компилируются только требуемые классы, но весь исходный файл требуемого класса должен быть корректным. На текущей машине установлен JDK 27.

## Goals / Non-Goals

**Goals:**
- Общий исходный производственный код для JVM-проверок и Android, без дублирования алгоритмов.
- Минимальный тестовый запуск на JDK 22+ со стандартной точкой входа, без preview-функций.
- Сохранение сценариев и диагностики неуспешного выполнения.

**Non-Goals:**
- Эмуляция Android, перенос instrumentation-проверок на JVM или замена проверок камеры и жизненного цикла устройства.
- Новый тестовый фреймворк, автоматическое обнаружение тестов, изменение компилятора либо внешних пакетов сборки.

## Decisions

### 1. Единое дерево Java-исходников и source-file launcher

Добавить отдельный тестовый build-файл Y2K, использующий существующий `make/makefile` с Java-target. Генерировать `src` и Y2K-тесты в общий `.build/unit/src`, runtime предоставляется тем же генератором. Namespace и относительный путь каждого теста должны совпадать. Разные namespace приложения и тестов исключают перезапись файлов.

Запускать один исходный файл точки входа через `java .build/unit/src/argent/checks/runner.java`. Он явно вызывает все группы тестов. Производственные Android-файлы могут быть сгенерированы в том же дереве, но не должны быть достижимы из тестовой точки входа: launcher их не компилирует. Это позволяет использовать текущий генератор без нового механизма фильтрации файлов.

`make test` сначала генерирует Java и runtime, затем запускает launcher. Eval используется только для чтения тестового build-файла и генерации Make-правил. Ошибка любого этапа останавливает команду. Отдельного `javac`, каталога `.class` и зависимости от APK нет.

Альтернативы: отдельный `javac` противоречит желаемому запуску; Gradle/JUnit добавляют лишнюю инфраструктуру; объединение всех Java-классов в один файл усложняет namespace и не нужно на JDK 22+.

### 2. Тесты на Y2K, стандартный main и явные проверки

Перенести `.eval` в функции `run` именованных Y2K-модулей под `test/argent/checks/`. Для точки входа использовать минимальный top-level `raw-code`, добавляющий `public static void main(String[] args) throws Exception` в сгенерированный класс и вызывающий обычную Y2K-функцию набора. Вложенный `gen-class` не подходит для прямого source-file запуска: launcher выбирает верхнеуровневый класс.

Общий небольшой helper проверяет условие и выбрасывает `AssertionError` с названием сценария. Не использовать Java `assert`, зависящий от `-ea`, и eval-only `assert`. Последовательно вызывать все группы, печатать их успех и итоговый успех только после завершения всего набора. Функции передавать через явные лямбды там, где этого требует Java-target.

Альтернатива — переписать сценарии на Java; это теряет желаемое сохранение Y2K. Java-host вставки ограничены необходимой точкой входа и JDK-интероперабельностью.

### 3. Один платформонезависимый модуль QR-запроса

Перенести тело `request` в `src/argent/vendor/qr_request.clj` без Android-импортов. `qr_image.clj` использует этот модуль для запуска и остановки запроса, сохраняя камеру и публичный контракт адаптера. Тесты напрямую используют новый модуль. Состояния, callbacks, порядок освобождения и строки логов сохраняются.

Подмена `android.*` и SDK заглушками либо подключение Android jar не нужны: препятствие находится в границе исходного файла, а алгоритм уже принимает зависимости через `io`.

### 4. Проверять реальный stderr средствами JDK

Перенести ожидания из `logging.py` в Y2K-группу на JVM. Захватывать `System.err` в `ByteArrayOutputStream` через `PrintStream`, выполнять реальные операции и сравнивать строки в прежнем порядке. Восстанавливать исходный stderr в `finally` через минимальный host-helper, чтобы падение теста сохраняло видимую диагностику. Выполнение последовательное; параллелизм не вводится.

Сохранить проверки границ вложенных операций, отсутствия вывода до исполнения и на пустой очереди, порядка событий очереди и QR. Нельзя заменять захват реального вывода тестированием собственной функции форматирования. Python-процесс и eval для этого больше не нужны.

## Risks / Trade-offs

- Различия eval и Java-target в типах, функциях и равенстве → переносить ожидания по смыслу сценариев; не ослаблять их ради успешной компиляции. Ошибку компилятора, если обнаружится, фиксировать как блокер, не скрывать eval-fallback.
- Source launcher компилирует только достижимые классы → runner явно ссылается на каждую группу; отдельно сохраняется Android-сборка для платформенных исходников.
- Попадание JVM-only тестов в Android-сборку через существующий `test` каталог → удалить генерацию `test` из Android-конфигурации `build.clj`, оставив её отдельному тестовому build-файлу. В репозитории `argent.counter` вызывается только из `counter.eval`; instrumentation-тесты из `test/android` от него не зависят. Успешная сборка приложения и instrumentation подтвердит совместимость с внешним образом сборки.
- Захват stderr меняет глобальное состояние JVM → запускать проверки последовательно и восстанавливать поток даже при исключении.
- Перенос QR-логики затрагивает приложение → после локальных проверок собрать APK и проверить реальную камеру, результат, отмену, повторный запуск и остановку владельца на физическом устройстве.

## Migration Plan

1. Выделить QR-логику и перенести существующие сценарии в JVM-совместимые функции, сохранив соответствие старым группам.
2. Подключить отдельную генерацию тестового дерева, runtime и source-file запуск; проверить чистый и повторный запуск, а также ненулевой код при намеренно нарушенном ожидании.
3. Переключить `make test`, сохранить связь `make check`, удалить заменённые eval-файлы и Python-проверку логирования, обновить `docs/testing.md` с JDK 22+ и границей локальных/device-проверок.
4. Проверить Android-сборку и изменённый QR-сценарий на физическом устройстве. Отсутствие устройства оставляет эту проверку незавершённой.

Данные приложения и формат очереди не мигрируют. Откат состоит в возврате прежнего тестового запуска и размещения QR-функции.
