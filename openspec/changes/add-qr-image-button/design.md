# Design

## Context

Мотивация описана в `proposal.md`. Проект компилирует Y2K Language в Java через `ly2k`; Android-зависимости заданы в `resources/android.clj`. `MainActivity` наследует обычную `android.app.Activity`, а `vendor/view.clj` создаёт и обновляет нативные View по тегам. `vendor/chat.clj` отключает кнопки старых сообщений. Получения результатов внешних Activity и QR-декодера пока нет.

Существующая спецификация `operation-dispatch` не требует изменений: асинхронный выбор не становится сохраняемым бизнес-событием. Тест `test/counter_device.py` сейчас предполагает ровно три кнопки на сообщение и только числовые TextView; пример QR потребует уточнить эти селекторы.

## Goals / Non-Goals

**Goals:** минимальная интеграция в текущий рендерер, один запрос выбора за раз, строковый callback, отсутствие зависимости вызывающего кода от типов ML Kit.

**Non-Goals:** камера, собственный bottom sheet, интерпретация содержимого QR, поддержка других штрихкодов, сохранение незавершённого запроса после уничтожения Activity, fallback на другой декодер. Отмена, отсутствие QR, несколько QR и ошибки вне успешного сценария не получают отдельного продуктового поведения.

## Decisions

### 1. Тег компонента и callback

Предлагаемый API: `:qr-image-button` с `:text`, `:description` и `:onresult`. По аналогии с существующим `:onclick`, `:onresult` получает строку и возвращает операцию, которую рендерер запускает с окружением `w`. Так listener может пользоваться текущими `fx/dispatch` и подменяемыми зависимостями; объект `Barcode` не выходит за границу интеграции.

Переиспользовать создание обычного `Button`, включая отступы и доступность. Добавить поддержку тега в обе ветви рендерера — `create` и `update!`. Замыкание для запроса фиксируется при нажатии; последующее нажатие использует обновлённый listener. Отдельный класс виджета не нужен.

### 2. Системный выбор через текущую Activity

Использовать платформенный intent Photo Picker для одного `image/*` и передавать результат из `onActivityResult` в небольшой модуль `vendor/qr_image.clj`. Для текущей обычной Activity это меньше изменений, чем миграция на AndroidX `ComponentActivity` ради launcher API. Устаревший механизм результата здесь — осознанный компромисс минимального изменения.

Держать единственный незавершённый callback в экземпляре платформенной интеграции, без глобального состояния и реестра запросов. Открытие доступно через именованную операцию окружения, принимающую callback. URI используется в текущем запросе; постоянное право доступа и копирование изображения не нужны.

Допущение совместимости: устройство имеет работающий системный Photo Picker. Поддержка устройств без него не входит в итерацию; версию compileSdk и доступность соответствующего intent проверить при сборке, не повышая minSdk без необходимости.

### 3. ML Kit через Google Play services

Подключить `com.google.android.gms:play-services-mlkit-barcode-scanning:18.3.1`, настроить только `FORMAT_QR_CODE`. После выбора картинки обеспечить установку модели через `ModuleInstallClient`, затем создать `InputImage.fromFilePath(context, uri)` и вызвать `scanner.process`. Успешный результат передать через `getRawValue()` ровно один раз в UI-потоке.

Не считать окончание запроса установки доказательством загрузки: если установка асинхронная, дождаться завершения через API состояния установки. При уже доступной модели сразу продолжить. Это работает и при sideload, в отличие от расчёта только на manifest-предзагрузку при установке из Play Store. Добавить прямую зависимость API установки, если она нужна для используемых импортов.

Чтение/декодирование изображения не должно блокировать UI; ресурсы scanner и слушатели установки освобождаются при завершении либо уничтожении владельца. Не вводить отдельную архитектуру фоновых задач.

Альтернативы: ZXing отклонён в пользу выбранного пользователем Google API; bundled ML Kit увеличивает APK и не соответствует выбору Play services; Google Code Scanner запускает собственный камерный UI и не принимает выбранный URI.

### 4. Минимальный пример и проверка

Добавить на текущий экран кнопку «QR из картинки»; пример listener показывает полученный текст коротким системным Toast через операцию окружения. Это предложенная деталь демонстрации, не новый формат доменного состояния. Проверка должна наблюдать точную строку и однократный вызов callback, а также повторное использование кнопки после обновления экрана.

Оставить одну воспроизводимую проверку успешного потока с известным QR-изображением. Обновить существующие device-проверки на адресные селекторы счётчика вместо общего числа кнопок, сохранить их проверки очереди и отключения старых сообщений.

## Risks / Trade-offs

- [Модель ещё не загружена] → ожидать готовности в том же запросе; проверить sideload на физическом устройстве. Наличие сети при первой загрузке — предусловие.
- [Play services или Photo Picker отсутствуют] → такие устройства вне текущего успешного сценария; собственный fallback не добавляется.
- [Асинхронный callback переживает Activity] → очистить ссылку на listener и ресурсы при уничтожении владельца; восстановление незавершённой операции не обещается.
- [Java API и перегрузки могут ограничиваться ly2k] → проверить компиляцию интеграции на раннем шаге, используя существующие типизированные Java-listener паттерны.

## Migration Plan

Миграция данных не нужна. Добавить зависимость и интеграцию, собрать APK, установить на физическое устройство и проверить выбор картинки, точную строку результата и существующий счётчик. Откат — удаление нового компонента, интеграции и зависимости без изменения данных приложения.
