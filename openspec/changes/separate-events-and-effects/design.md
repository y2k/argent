# Design

## Context

Мотивация описана в `proposal.md`. Изменение затрагивает механизм вызова, прикладные обработчики и Android-адаптеры, поэтому требует общего дизайна.

Сейчас обе регистрации создают адаптеры `(env, arg) → result`, а `event/dispatch` исполняет любой адаптер. `event/register` дополнительно исполняет вычисление, возвращённое обработчиком. `chat/start` возвращает такие вычисления для доступа к окружению View, поэтому платформенная отрисовка ошибочно относится к событиям. `toast/show` напрямую вызывает адаптер из `fx/summon`, обходя общий путь логирования.

Действующий контракт `operation-dispatch` требует универсального вызова. Delta осознанно заменяет это требование отдельными публичными API, сохраняя общие свойства исполнения.

## Goals / Non-Goals

**Goals:**
- Различать события и эффекты по API и семантике исполнения, а не только переименовать универсальный диспетчер.
- Сохранить один `env` и разрешение зависимостей в момент запуска отложенного вызова.
- Сделать отрисовку обычным действием, сохранив рабочее окружение кнопок и изоляцию экземпляров.

**Non-Goals:**
- Отдельные реестры, типовые теги и проверки неправильного API, совпадающих или отсутствующих имён.
- Составные эффекты, списки эффектов для отдельного интерпретатора, новый scheduler или обязательная очередь для каждого вызова события.
- Изменение хранения событий, контрактов QR, UI-поведения и формата диагностических строк.

## Decisions

### 1. Хранить публичные функции в общем окружении

`fx/register` сохраняет обычную функцию `arg → result`; `event/register` сохраняет обработчик `arg → computation`. Оба используют существующий плоский `env`. Имена уникальны, правильный API выбирает вызывающая сторона; поведение неправильного вызова не определяется.

`fx/call` создаёт вычисление `env → result`: на запуске извлекает функцию, передаёт аргумент и возвращает значение как есть. `event/dispatch` создаёт такое же по внешней форме вычисление, но после вызова обработчика исполняет полученное вычисление с тем же `env`. Регистрация и создание вызовов не исполняют пользовательские функции.

Альтернатива — сохранить универсальные адаптеры и сделать `fx/call` псевдонимом диспетчера — оставляет смысловое смешение. Два реестра и типовые проверки усложняют согласованное разделение API. Простое хранение функций позволяет обойтись без обоих вариантов.

### 2. Сохранить композицию вычислений

`fx/next` и `fx/pure` сохраняют текущую роль. Обработчики связывают вызовы эффектов через `fx/next`; наличие отложенной обёртки у вызова не делает зарегистрированный эффект составным. Возвращённая эффектом функция остаётся обычным значением.

`application` сохраняет служебные точки входа `:app:start!`, `:app:handle-event!`, `:app:render!`; это функции жизненного цикла, а не зарегистрированные составные эффекты. `:app:render!` по-прежнему координирует чтение состояния и эффект отрисовки. Прямой переход от `:ui:start` к событию `:chat:new-message` сохраняется.

### 3. Подключить окружение чата при сборке экземпляра

В `app/run` уже есть локальный atom `application`, заполняемый до `:app:start!` и запуска pump. Создать его до `chat/start` и передать чату функцию получения текущего экземпляра. Обычные функции добавления и обновления сообщения получают только `node`, получают окружение через это замыкание и сразу вызывают существующие View-функции. Оба действия возвращают `nil` и регистрируются через `fx/register`.

Ссылка принадлежит одному `run`; глобальное окружение не вводится. Предусловие: приложение собрано и ссылка заполнена до первого вызова чата. `application/create` сейчас только собирает окружение и не вызывает чат, что позволяет сохранить порядок инициализации.

Это замыкание на платформенную зависимость, а не составной эффект: действие не возвращает вычисление и механизм эффектов не исполняет его результат. Альтернатива с передачей окружения каждому публичному эффекту нарушает выбранный контракт одного аргумента; второй API регистрации прямо исключён обсуждением.

### 4. Мигрировать вызовы по назначению

| Назначение | API |
| --- | --- |
| `:ui:start`, `:chat:new-message`, `:domain:increment`, `:domain:decrement` | `event/register`, `event/dispatch` |
| `:state:update`, `:chat:append-message`, `:chat:render-message` | `fx/register`, `fx/call` |
| `:qr:pick`, `:ui:toast` | `fx/register`, `fx/call` |
| `:ui:dispatch`, `:domain:dispatch` — постановка в очередь | `fx/register`, `fx/call` |

`view_node` запускает QR через `fx/call`, сохраняя окружение нажатия для callback. `toast/show` становится тонкой обёрткой над `fx/call`. `view/create` и `view/update!` остаются внутренними View-функциями; переписывать рендерер не требуется.

Заглушки тестов должны соблюдать ту же классификацию: нельзя подменять событие обычным эффектом или эффект композиционным обработчиком. Проверки передачи окружения чату адаптируются к новой явной связи через сборку, сохраняя проверку поведения кнопок.

### 5. Сохранить трассу для обоих путей

Оба публичных вызова пишут существующие `Argent op.begin name=...` и `Argent op.end name=...` вокруг фактического исполнения. Для события завершение пишется после вложенного вычисления; для эффекта — после возврата обычной функции. Создание вызова ничего не пишет. QR callback остаётся отдельным асинхронным этапом. Вызов Toast через `fx/call` получает такую же трассу, как остальные эффекты.

Новые категории логов и универсальный публичный диспетчер для переиспользования логирования не нужны.

## Risks / Trade-offs

- [Окружение чата запрошено до завершения сборки] → Заполнять существующий atom до старта приложения и pump; проверить старт и реальные кнопки сообщения.
- [Смешанные регистрации в старых тестовых заглушках маскируют ошибки миграции] → Обновить регистрации по назначению и сохранить проверки подмены, результата-функции и изоляции экземпляров.
- [Один `env` не запрещает неправильный API технически] → Это сознательная граница текущего изменения: контракт описывает успешный путь, без реестров и защитных проверок.
- [Окружение внутри Android-адаптера привязано к экземпляру] → Для подмены его зависимостей собирать отдельный экземпляр; динамическая подмена самих эффектов в переданном `env` сохраняется. Не вводить глобальную ссылку.

## Migration Plan

1. В одной итерации изменить регистрации и вызовы, платформенные адаптеры, тестовые заглушки и актуальный пример QR. Совместимый универсальный вызов не оставлять.
2. Запустить `make check`, собрать APK через `make build` и установить на физическое устройство.
3. Проверить сценарии счётчика, доставки сохранённых событий и сообщений через `test/counter_device.py`, компонент QR через `test/qr_component.sh`, реальную камеру и Toast вручную. Подтвердить вложенную трассу событий и эффектов.
4. При откате вернуть изменения исходников и собрать предыдущую версию. База очереди и имена событий не меняются, миграция данных не требуется.
